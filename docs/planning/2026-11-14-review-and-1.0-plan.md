# Project review and plan to 1.0 — 2026-11-14

> **Status: decided, in progress.** Decisions D1–D5 accepted as recommended
> (2026-11-14); step B done. Written after SDK and CLI 0.6.2, the first releases
> from the public repository. It replaces the
> [developer experience review](../history/2026-11-12-developer-experience-review.md)
> as the open plan: that review was carried out through 0.6, and its 1.0
> part continues here (§4). [`TODO.md`](../../TODO.md) §1 follows §4's order.

Scope: the whole project (the SDK, the CLI and its template, the site, the
release pipeline, the registry and the six reference widgets), judged as an
open-source project at the state of the art. It covers security, design,
code and process. Evidence is from the repositories, their CI and npm, as of
`main` at 684f029 (0.6.2).

## 1. Verdict

The code is in good shape:
- every check passes locally on `main`: SDK 262 tests, CLI 74, template 3,
  script tests 23, the examples' typecheck, lint, the size budget, the
  site's build, and the demo document checks;
- the published packages carry provenance, have no known vulnerability, and
  the SDK depends on `zod` only;
- the security review found nothing new (§2).

What holds the project back is no longer the code but the flow around it:
- **The reference widgets lag three minors behind.** Their `dev` is on SDK
  0.4.0, and the 0.5.0 work never reached it.
- **Releases outpace pnpm's 24-hour age.** There were six SDK releases in
  three days, which the widgets can't follow.
- **The repository's Dependabot pull requests stall.** CI never runs on
  them and Dependabot stops rebasing them.

1.0 needs those fixed first: its promise is that widgets keep up with the
SDK, and today the SDK's own reference widgets don't.

## 2. What was checked and holds

- **Supply chain:**
  - every action is pinned by SHA;
  - `persist-credentials: false`, except for the jobs that push;
  - least-privilege `permissions` in every workflow;
  - the single `pull_request_target` workflow never runs code from the pull
    request's branch;
  - `minimumReleaseAge` is seven days here and 24 hours in widgets;
  - install scripts run only for an allowlist;
  - the docs site's dev-only advisories are resolved through overrides; one
    low-severity deepmerge advisory remains, with no fix.
- **Publishing:** npm Trusted Publishing from a protected environment, with
  `fixed` versions for the two packages, provenance, tags and the template
  canary.
- **SDK runtime:**
  - no HTML injection sink and no `message` listener of its own;
  - `fetchWithAuth` sends the token to its own origin only;
  - attachment ids are validated;
  - the CLI runs commands without a shell, except on Windows, where it
    refuses arguments that aren't plain;
  - package names are validated before a registry lookup.
- **Code hygiene:**
  - one `eslint-disable` in the SDK, and no `TODO` or `FIXME`;
  - the largest SDK file is 523 lines;
  - the public names are pinned by `public-api.test.ts`.
- **Repository:** the `main` ruleset (pull request, `gate`, no force push),
  `SECURITY.md`, a code of conduct, issue and pull request templates,
  `CODEOWNERS`, and HTTP security headers on gristwidgets.com.

## 3. Findings

### 3.1 The reference widgets are behind (P1)

- **On `dev`:** all six are on `grist-widget-sdk` and
  `create-grist-widget` ^0.4.0.
- **In production:** `main` and `/latest/` are at 0.2.0.
- **The 0.5.0 work:** the bump, the template upgrade and the App exported
  only as default sit on `claude/great-tesla-x43xlw` in each repository,
  never merged into `dev`. Their CI was blocked by the Actions quota at the
  time, and the follow-up was lost.
- **Their own Dependabot pull requests:** nine are open, eight of them majors
  waiting for days:
  - jotai 3 (gantt);
  - `ai` 7, `@ai-sdk/openai` 4, motion 14, nanoid 6, `@streamdown/code` 2
    (ask-ai);
  - maplibre-gl 6 (world-map);
  - pdfjs-dist 6 (scan-with-ai).
- **Branch rulesets** on the widget repositories are still to be set
  (`TODO.md` §0).

The Real widgets workflow checks every SDK change against these widgets'
`dev`, which still calls the names 0.6 deprecated. That is useful while
the names exist. Once 1.0 removes them, the check fails until the widgets
have migrated: migrating the widgets is on 1.0's critical path.

**Action:**
- the six widgets on 0.6.2 (scheduled for 2026-11-15, starting from the
  unmerged 0.5.0 branches);
- a 0.3.0 release of each;
- the registry refreshed;
- each widget's Dependabot majors triaged by the widget's owner, one pull
  request at a time.

### 3.2 Release cadence versus the 24-hour age (P1)

| Version | Published (UTC) |
| --- | --- |
| 0.5.0 | 11-12 19:55 |
| 0.5.1 | 11-13 22:20 |
| 0.6.0 | 11-14 04:55 |
| 0.6.1 | 11-14 05:45 |
| 0.6.2 | 11-14 06:28 |

A widget may only install a version a day old. With releases hours apart,
an upgrade planned for one version lands after the next one, and each
widget upgrade is redone. Changesets already batch: the Version Packages
pull request accumulates every merged changeset until someone merges it.

**Action:**
- **A release train:** merge the Version Packages pull request once a
  week, or for a security fix.
- **`RELEASING.md` says so.**
- **Widgets upgrade once per train,** a day after it.

### 3.3 Dependabot pull requests stall in this repository (P1)

`dependabot-changeset.yml` commits a changeset onto Dependabot's branch.
Two consequences, both seen on #4 and #5:
- **CI never runs.** A push made with `GITHUB_TOKEN` leaves the runs
  waiting for approval, and `CHANGESET_PUSH_TOKEN` was declined.
- **Dependabot stops rebasing.** It no longer rebases a branch someone else
  committed to, so the first conflicting change on `main` strands the pull
  request.

Both pull requests ended superseded by hand (#11, #12).

**Action:**
- Retire the commit.
- `check-changeset.sh` accepts a pull request authored by `dependabot[bot]`
  without a changeset.
- Whoever prepares the release train adds one "routine dependency updates"
  changeset when a Dependabot change reached a published package (the
  template's `package.json`). The Version Packages pull request is the
  natural place to check.

### 3.4 Dependencies Dependabot can't see (P2)

The docs site's `fumadocs-ui` is an npm alias
(`npm:@fumadocs/base-ui@16.14.0`). Dependabot doesn't update aliases, so it
fell four minors behind `fumadocs-core` and left an unmet peer dependency.
#15 fixes it.

**Action:** `pnpm peers check` in CI's `repo` job, so a mismatch fails the
pull request that causes it.

### 3.5 Smaller findings (P2)

- **The template canary runs after every push to `main`,** published or
  not (#12 and #13 each re-scaffolded the same version). It is harmless,
  but it costs minutes and can mislead: it could skip when npm's `latest`
  is the version already on the canary repository.
- **The site's headers are only unit-tested.** Nothing checks what
  Cloudflare actually serves. A step after deploy (`curl -sI` on `/docs/`,
  `/examples/<id>/latest/` and `/grist-static/`) would catch a change in
  Cloudflare's handling of `_headers`.
- **Deprecated internals:**
  - `resetGristReadySingleton`'s old alias in `runtime/ready.ts`;
  - the upload helper `@deprecated` in favour of
    `extractAttachmentIdsFromUploadPayload`.

  These go with 1.0's removals.
- **`useGristSchema` takes connection options** (`requiredAccess`,
  `columns`, …) that a provider ignores, as the developer experience review
  noted (§3.8). It also still returns a deprecated `isAvailable`. 1.0 limits
  its options to the schema's own.
- **React 18 is declared (`>= 18`) but untested.**
- **No API report:** type changes don't show as API changes in review.
- Both are already in the 1.0 plan.

## 4. Decisions for the maintainer

Each came with a recommendation; **all five were accepted as recommended**
on 2026-11-14, and §5 follows them.

| # | Decision | Recommendation | Why |
| --- | --- | --- | --- |
| D1 | The page-wide connection (`useGrist()` outside a provider) | **Remove in 1.0:** deprecated with a warning in 0.7. `renderWithGrist` always renders a provider (a default declaration when `widget` is omitted). `useGristOptional()` stays for components that also run outside Grist. | `mountGristWidget` always renders the provider; the page connection serves only tests without `widget`, and makes "which options won" a puzzle |
| D2 | Release cadence | **A weekly train,** plus out-of-band security fixes | §3.2 |
| D3 | Changesets for Dependabot pull requests | **No bot commit;** a routine changeset per train | §3.3; the alternative is the PAT already declined |
| D4 | The path to 1.0 | **0.7.0 first,** holding every remaining deprecation and the 1.0 tooling. **Then 1.0.0,** removals only, once the six widgets run 0.7 without warnings. | The policy (deprecate for at least one minor) then holds for D1 too; 1.0 itself contains no surprise |
| D5 | The core widget library (`TODO.md` §2) | **After 1.0** | It should start on the stable surface |

## 5. Plan

Each step keeps the six reference widgets green (the Real widgets workflow,
`e2e:grist`) and ships its changeset.

| Step | Content | Done when |
| --- | --- | --- |
| **A. Catch up** (now) | The six widgets on 0.6.2 on `dev`, then released 0.3.0 (`dev` → `main`); the registry refreshed; the widgets' own Dependabot majors triaged; rulesets on the widget repositories | Every reference widget runs 0.6.2 in production with no deprecation warning |
| **B. Flow** | #15; retire the Dependabot changeset commit (§3.3); `pnpm peers check` in CI; the canary skips an unchanged version; a post-deploy headers check; the release train in `RELEASING.md` | A Dependabot pull request gets CI and merges without a hand-made copy |
| **C. 0.7.0** (the 1.0 candidate) | Page-wide connection deprecated (D1) and `renderWithGrist` always renders a provider; `useGristSchema` limited to schema options; an API report (`.d.ts`, api-extractor or equivalent) checked in CI; React 18 and 19 in the core job's matrix; the versioning policy in the docs; codemods for every 0.7 deprecation | The API report is green in CI and the policy page is published |
| **D. Widget tooling** | `grist-widget-sdk` and `create-grist-widget` grouped in the template's Dependabot config, with a widget CI job that runs `upgrade` on that pull request and commits the template's changes; `pnpm release <patch\|minor\|major>` for widgets (bump, changelog from merged pull requests, the `dev` → `main` pull request) | A widget takes a release train by merging one green pull request |
| **E. Widgets on 0.7** | The six widgets through D's flow | No deprecation warning in any of the six |
| **F. 1.0.0** | Every deprecated name removed; each break covered by a codemod `upgrade` runs; the API report's baseline reset | The six widgets upgrade by merging D's pull request |
| **G. Then** | The core widget library (`TODO.md` §2); the "later" items (config panel, secrets guidance, landing page with a live widget, error-message pass) | Scoped in its own plan |

### What the maintainer does

- **D1–D5:** decide (or accept the recommendations).
- **Repository settings:**
  - enable private vulnerability reporting;
  - dismiss the deepmerge alert ("no fix available, dev-only");
  - set the widget repositories' rulesets.
- **Approvals:** approve the Version Packages and Dependabot runs; give the
  production go for the widget releases.
