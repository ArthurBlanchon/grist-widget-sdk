### 0.3 What the iterations taught (robustification principles)

These are the patterns behind every incident this week — they should drive
how the remaining work (and all post-v1 work) is executed:

1. **Only live runs find onboarding bugs.** Every real defect shipped this
   week — scaffold committed to the wrong branch, npm silently stripping
   `.gitignore`, missing `packageManager` breaking the first CI run, the
   blank showcase page (project-site base paths), `/template/dev/` never
   having gone live, `deploy.yml`'s very first real run on a real widget
   repo failing outright with "Dependencies lock file is not found", and
   now a real scaffolded widget's own bare site root 404ing instead of
   showing the template's showcase hub — passed every sandbox check and
   was caught only by running the real path (live scaffold, real deploy,
   headless browser on the real URL shape). The lockfile one is the
   starkest example yet: the CLI's auto-commit runs before anyone's first
   `pnpm install`, so a freshly scaffolded repo never has a committed
   `pnpm-lock.yaml`; `actions/setup-node`'s `cache: pnpm` and `pnpm install
   --frozen-lockfile` both hard-require one, and the CLI smoke test only
   ever checked `pnpm install && build` locally — never the actual GitHub
   Actions workflow — so this sat invisible through every prior CI run.
   Fixed by dropping both requirements; `scripts/smoke/create-widget.sh`
   now asserts they never reappear (assertion verified against the actual
   regression: reverted the fix, confirmed the smoke test fails with the
   same error class, restored it). The bare-root one is the same shape one
   layer deeper: `main.tsx` was explicitly written to render the showcase
   hub at any URL with no recognized channel suffix, including the site
   root, but the standalone `deploy.mjs` bundled into every scaffold never
   actually placed a build there — only the monorepo's own
   `template-showcase.mjs` variant did, and only *it* was smoke-tested for
   the hub path. Fixed by mirroring that root-placement logic into the
   standalone script; `scripts/smoke/template-deploy.sh` now asserts the
   root `index.html` lands too. Immediately after that fix went live, the
   *next* layer surfaced: `template-widget`'s GitHub Pages setting was on
   `main` instead of `gh-pages`, serving raw unbuilt source (a blank page,
   `/src/main.tsx` 404) — a manual one-time step that was already
   documented in five places, but none of them warned against this
   specific mistake, so it wasn't caught by reading the docs either. All
   five now do. **Rule: any change to the onboarding path gets one live
   end-to-end validation after merge** (the
   `run-grist-widget-template-deploy` skill exists for exactly this) —
   and as of this same incident, that rule is now partially automated:
   `.github/workflows/template-canary.yml` runs the same live check
   itself after every release, against a standing public reference repo
   (`grist-widget-template`) instead of a throwaway one, so the next
   regression in this family gets caught the same day it ships, not the
   next time someone happens to run the skill by hand. Confirming the
   point immediately: before that canary was even wired into CI, the very
   next live look at the freshly-scaffolded reference repo found one more
   instance of the same family — the showcase hub's version index and
   "dev"/preview links were hardcoded to the monorepo's own
   `/grist-widget-sdk/template/...` URLs, so a real scaffold's landing page
   showed the *monorepo's* released versions instead of its own (and, one
   layer deeper again, the standalone `deploy.mjs` never even generated a
   `versions.json` to point at correctly). Fixed by deriving those URLs
   from the current deploy's own path instead of a hardcoded one, and
   generating `versions.json` from the standalone pipeline too — exactly
   the shape of bug `template-canary.yml` exists to catch automatically
   from here on.
   Pending under this rule: the new copyable `CLAUDE_CODE_PROMPT` has never
   been live-tested — its scaffold-into-subdirectory-then-push-to-origin
   flow should be validated once with a real Claude Code session.
2. **Silent no-ops are the dominant failure class.** Merge-without-bump
   publishes nothing (by design, but invisibly); a new branch with no novel
   commits fires a push event with an empty commit list, so paths-filtered
   workflows silently never run; vitest passes green on a project with no
   test files (the still-open docs-test gap); npm strips `.gitignore`
   without a warning. **Rule: every "should have happened" needs a loud
   assertion somewhere** — the smoke tests now assert placements and
   `versions.json` contents; the docs-test gap fails this rule and that's
   why it's promoted to a v1 blocker below.
3. **Every user-facing change carries a changeset** (learned via PR #12
   shipping without one) — now habitual; the release train ran ~10 clean
   cycles on it.
4. **Platform constraints beat design docs.** The original showcase plan
   (root deploy, `workflow_run` trigger, registry-installed build, separate
   app) was ~fully rewritten by contact with reality: GitHub Pages
   project-site base paths, no actual registry race, "reuse the template as
   its own showcase". The approved-plan file
   (`so-your-idea-is-flickering-church.md`) is retained as history but is
   superseded — this document is the source of truth.
5. **Short feedback loops paid for themselves immediately** — the permanent
   `dev/template-showcase` branch and per-widget `dev/` channels turned
   every review round from "cut a release" into "push a branch".

## 2. Decisions to make (previous choices challenged)

### D1 — Onboarding model: external-first, monorepo second

Today everything implicitly assumes "your widget lives in this monorepo"
(workspace deps, per-widget deploy workflows here, template README half-full
of monorepo notes). That model cannot scale to external developers: they
would need push access, their deploys would ride this repo's CI, and their
widgets would upgrade whenever `packages/core` moves.

**Decision: support two explicit models, external-first.**

- **External (primary, the v1 product):** scaffold the template (`npm create
  grist-widget`) into *their own repo*, depend on `grist-widget-sdk` from npm
  with a caret range, deploy to *their own* GitHub Pages with a deploy workflow
  **shipped inside the template**. They upgrade the SDK when they choose
  (`pnpm up`).
- **Monorepo (contributor model):** adding a widget under `widgets/` here is
  for contributing to the shared gallery, not the default way to build one.

This single decision resolves most of the tension: the SDK can keep evolving
fast because external users are isolated behind npm semver, and this repo's
CI only has to serve *your* widgets.

### D2 — Unified widget deploy workflow: versioned releases + dev channel

> **Implemented (2026-07-11)** on `claude/grist-widget-sdk-v1-8xle4o`:
> `.github/workflows/deploy-widgets.yml` + `scripts/deploy/publish.mjs` replace
> the seven `deploy-*.yml` files; both channels, the manifest, and the
> self-reload snippet are in place, and widgets carry `grist` metadata blocks.
> Verified in-sandbox (helper unit tests, full publish dry-run against a real
> `gh-pages` clone, concurrent-push rebase-retry, browser self-reload, root
> `pnpm test`). The subsections below remain the strategy + robustness rationale.

Replace the seven copy-pasted `deploy-*.yml` files (identical modulo
`WIDGET_NAME`) with **one** `deploy-widgets.yml` serving two channels from the
same build logic:

- **Release channel — push to `main`.** Release-driven and *immutable*: a
  version is built once and never overwritten.
- **Dev channel — push to `dev/<widget>`.** A mutable scratch URL
  (`/<widget>/dev/`) for reviewing the widget inside a real Grist document.
  Agent-driven loop: agent pushes to `dev/<widget>` → CI builds → the URL
  updates → the reviewer watching the Grist doc sees it (self-reload, below).
  No watch process, no tunnel — the push *is* the iteration signal.

**gh-pages layout:**

```
gh-pages/
  manifest.json                  # Grist widget-repository manifest (release only)
  gantt/
    latest/    → alias to the newest release (mutable, opt-in auto-upgrade)
    dev/       → newest dev build + version.json + self-reload (mutable, scratch)
    v0.1.0/    → immutable
    v0.2.0/    → immutable
  news-feed/
    …
```

**Triggers & idempotence.** One job, `on: push: [main, "dev/**"]` +
`workflow_dispatch`:

- `main` → enumerate `widgets/*/package.json`, read each `version`; for each
  widget whose `v<version>` dir does **not** exist on gh-pages: build
  `--base "/<repo>/<widget>/v<version>/"`, copy to `v<version>/`, refresh
  `latest/`, regenerate `manifest.json`.
- `dev/<widget>` → resolve the widget from the branch name (strip `dev/`,
  match a `widgets/<name>` dir, else fail listing valid names); build
  `--base "/<repo>/<widget>/dev/"`, copy to `dev/`, write `version.json`,
  inject the self-reload snippet. Dev builds never touch `latest/` or the
  manifest.
- All paths end in **a single git push** of the `gh-pages` working tree.

Consequences, all desirable:

- **Releasing a widget = bumping its `package.json` version** in the same PR
  as the change. No version bump → no deploy. `packages/core` changes stop
  auto-redeploying all seven widgets (today's behavior, and the riskiest
  thing in the repo while the SDK is unstable) — a core-only push to `main`
  is a **no-op deploy run**.
- Users pin `…/gantt/v0.2.0/` in Grist and upgrade by editing the URL;
  `…/gantt/latest/` remains for people who want auto-upgrades. Old versions
  keep working forever (built artifacts freeze the SDK they were built with,
  so an SDK regression can never retroactively break a deployed widget).
- Rollback = point `latest/` back one version (a `workflow_dispatch` force
  run), or just tell users the previous pinned URL — which never moved.

**Self-reload (dev channel only).** At publish time, inject a tiny
dependency-free IIFE into `dev/index.html` carrying that build's short SHA. It
polls `version.json?ts=<now>` (`cache: "no-store"`, unique query defeats the
Pages/Fastly CDN's 600 s TTL) every ~5 s; when the served SHA differs from its
own baked-in SHA it calls `location.replace()` with a `__dev=<sha>` param
**merged into the existing query string** (so Grist's own iframe params
survive) — the unique URL busts the index.html cache, hashed assets are fresh
by filename, and the widget hot-swaps inside the Grist doc with zero clicks.
Prod builds are byte-identical to today (nothing injected).

**Grist widget-repository manifest** (release channel). Publish
`manifest.json` at the gh-pages root in the `gristlabs/grist-widget` format
(**verify exact field names against that repo during implementation** — at
least `widgetId`, `name`, `url`, `accessLevel`; likely also `published`,
`requiredAccess`, `columns`). One entry per widget that has a `latest/`, with
an **absolute** `url` (`https://<pages-host>/<repo>/<widget>/latest/`) to
avoid base-resolution ambiguity, sorted by widget id for minimal diffs.
Self-hosted Grist can then set `GRIST_WIDGET_LIST_URL` to this file and get
the gallery in the built-in picker. Per-widget opt-out via
`"grist": { "private": true }` in a widget's `package.json` keeps demos
(e.g. `v0-minimal-demo`) deployed but out of the public picker; default is
included.

**Robustness (the design's failure modes, each closed):**

1. **gh-pages write races.** `concurrency: { group: pages-gh-pages,
   cancel-in-progress: false }` serializes runs (main + several dev branches
   queue instead of racing). Belt-and-suspenders: the publish step clones
   fresh, commits, and pushes inside a **rebase-and-retry loop (×4, backoff)**
   so any interleaving push still lands. This replaces the undocumented
   `concurrency.queue: max` key (not in the Actions schema — the current runs
   pass, but it is not load-bearing) with a structural guarantee.
2. **Immutability under re-push.** A release build is skipped whenever
   `v<version>/` already exists, so re-pushing `main` without a version bump
   never rebuilds or overwrites a shipped version. Recovery for a corrupt
   `latest/` is the explicit `workflow_dispatch` `force` input, not an
   accidental overwrite.
3. **One broken widget must not block the others.** On a multi-widget `main`
   run, build each target independently, collect failures, **publish every
   success in the single push**, then exit non-zero so the run still goes red.
   A failing widget C never holds back A/B/D's releases.
4. **Dev-branch name parsing.** `dev/**` also matches `dev/gantt/spike`;
   resolve by longest match against real `widgets/*` dirs, then first path
   segment, else fail fast with the valid widget list. Deterministic, no
   diff-detection, parallel `dev/*` branches never collide (distinct `dev/`
   dirs).
5. **Self-reload cannot wedge the widget.** The poller is wrapped in
   try/catch and swallows fetch errors / 404s (transient CDN, first-deploy
   race) — it never crashes the widget. No reload loop: each build's snippet
   compares against *its own* baked SHA, so once the new build loads it
   matches and stops. It only ever *adds* `__dev`, never drops Grist's params.
6. **Fresh / empty gh-pages.** If the branch is absent (matters for the
   template's copy of this workflow on a brand-new external repo), create it
   as an orphan before publishing. Existing unversioned dirs here
   (`/gantt/`, …) are left untouched so current embeds keep working; the
   first release run adds `v<version>/` + `latest/` alongside. Bare URLs are
   documented as deprecated in favor of `latest/` or a pinned version.
7. **Zero-dependency publish step.** `scripts/deploy/publish.mjs` uses only
   `node:fs` / `node:path` / `node:child_process` — no npm install for the
   publish itself, so a registry hiccup can't break deploys. Runs under the
   default `GITHUB_TOKEN` (`permissions: contents: write`); pushing with that
   token does not retrigger `push` workflows, so there is no deploy loop (the
   `pages build and deployment` dynamic run on gh-pages is GitHub's own and
   expected).
8. **Base-path coupling.** `--base` derives from
   `${{ github.event.repository.name }}`; a future custom domain / CNAME would
   drop the repo segment. Documented so a rename or domain move is a conscious
   one-line change, not a silent 404.

Housekeeping: old immutable versions accumulate cheaply; optionally
garbage-collect superseded pre-1.0 versions or cap retained versions per
widget once the list is long. Stale `dev/` dirs from deleted branches are
harmless scratch (self-reload simply stops seeing SHA changes) and can be left
or swept later.

### D3 — SDK release engineering: npm + changesets

The changelog discipline is excellent, but manual (task-090) and unreleased.
Adopt `@changesets/cli`:

- Each PR that touches `packages/core` adds a changeset file (patch/minor +
  human-readable note — same habit as today's CHANGELOG entries, but machine-
  consumable).
- A release workflow (existing open **task-092**) turns accumulated
  changesets into: version bump, CHANGELOG section, git tag `v*`, GitHub
  Release, and `npm publish`.
- **Publish mechanism decided (2026-07-11): Trusted Publishing (OIDC), not a
  stored `NPM_TOKEN`.** npm is deprecating 2FA-bypass CI tokens (account
  actions ~Aug 2026, direct publishing ~Jan 2027), so OIDC is the future-proof
  path — short-lived creds, no secret. **Implemented** as `@changesets/cli` +
  `.github/workflows/release.yml` (`changesets/action`): merging PRs (each with
  a changeset) accumulates a "Version Packages" PR; merging that publishes over
  OIDC + tags + GitHub Release. Changesets generates
  `packages/core/CHANGELOG.md` (the npm-facing package changelog); the root
  `/CHANGELOG.md` stays the hand-curated broader project history — split by
  audience, decided 2026-07-12. `--provenance` deferred while the repo is
  private. Remaining: the one-time manual first publish (done for 0.2.0) +
  configure the npm Trusted Publisher (`RELEASING.md`).
- **Live incident, fixed 2026-07-12:** `release.yml` crashed on the first push
  to `main` after `0.2.1` shipped — `npm@latest` had silently become npm 12,
  whose changed `npm info --json` shape (array-wrapped, not a bare object)
  breaks `@changesets/cli@2.31.0`'s already-published check. Reproduced and
  confirmed directly (npm 11.6.2 handles it correctly, 12.0.1 doesn't); pinned
  `npm@^11.5.0` in `release.yml`'s "Upgrade npm" steps. This would
  have refired on every future push to `main` until fixed. See CHANGELOG.
- **Staging/rc publishes + real-widget CI, decided/built 2026-07-12.**
  Originally a separate `publish-staging.yml`: on any non-`main` branch,
  bumping `packages/core/package.json` to `X.Y.Z-rc.N` publishes exactly that
  prerelease to npm tagged `next` (never `latest`) over the same OIDC path —
  installable in a real codebase before it's a real release, with no
  persistent toggle to forget (the version string itself is the one-shot
  signal; nothing is committed to git). Considered and rejected: a
  `staging`/`prod` flag (in `package.json` or `.changeset/pre.json`-style pre
  mode) — both are persistent state that silently governs *every* subsequent
  release, including unrelated ones, until manually reverted; a prerelease
  version string has no such blast radius. Also added: `core-ci.yml` now
  builds every real `widgets/*` package (workspace-linked) on any PR touching
  `packages/core` — previously no CI built the real product widgets against
  an SDK change at all, only the playground demos and the template.
- **Live-tested, then merged into `release.yml`, 2026-07-12.** Live-testing
  `publish-staging.yml` surfaced a hard npm platform constraint: Trusted
  Publishing trust is scoped to an exact `repo + workflow file` pair, and
  npm's UI only allows **one** trusted workflow file per package — a second
  file can't be registered as a trusted publisher alongside the
  already-trusted `release.yml`, no matter how its `permissions:` are set.
  Fixed by folding the staging/rc-publish job into `release.yml` itself as a
  second job (`publish-staging`, gated `if: github.ref != 'refs/heads/main'`,
  next to `release` gated to `main`) and deleting the standalone file — no
  npm-side reconfiguration needed, since `release.yml` was already trusted.
  See CHANGELOG.
- 0.x semver is your friend during onboarding: external users on `^0.3.0`
  only receive `0.3.x` patches automatically. Breaking changes go in `0.4.0`
  and reach nobody until they opt in. This is precisely the safety valve
  needed for "the SDK will still change a lot while people build on it".

Prerequisites to first publish: ✅ `LICENSE` (MIT) added and shipped in the
tarball via `prepack`; `engines` left deliberate (core ≥ 18 consumers, root
≥ 22 dev). The package is already well-shaped for publishing
(ESM+CJS, subpath exports, types, `sideEffects: false`; primary entry is

### D4bis — Live dev loop in real Grist from cloud sessions

Reference workflow (local machine): `vite dev` + ngrok → paste the HTTPS URL
into a dev Grist cloud document → HMR straight inside Grist. The question is
how to reproduce this when development happens in a Claude Code cloud
sandbox.

Empirical constraints of those sandboxes (verified in-session): no inbound
connectivity; all egress goes through a TLS-re-terminating, policy-enforcing
proxy; under the default policy only package registries and the scoped GitHub
repo are reachable (ngrok/localtunnel/Cloudflare edges are blocked); the
container is ephemeral. Network policy is configurable per environment.

**Primary loop — push-driven dev channel (no watch, no tunnel). Implemented
2026-07-11** as the dev channel of D2's `deploy-widgets.yml`. Chosen because
iterations here are *agent-driven*: an agent finishing an edit already produces
a commit, so a `git push` is the natural "iteration done" signal — there is
nothing for a file-watcher to add. The mechanism is that dev channel, not a
separate system:

1. **Stable dev URL per widget** — `/<widget>/dev/` on gh-pages, works under
   any network policy (no Cloudflare/tunnel egress needed). Paste it once into
   a dev Grist document; it survives ephemeral sessions because it lives on
   gh-pages, not on a per-session tunnel.
2. **Publish = push to `dev/<widget>`.** CI builds and updates `/<widget>/dev/`
   in ~60–90 s. Same build path as release, so "works in dev" means "will
   work in release".
3. **Self-reload (D2)** swaps the widget inside the open Grist doc when the new
   build lands — the reviewer watches the document and it updates itself, no
   refresh.

Every agent iteration shows up in real Grist ~1–2 min later, reviewable by
anyone the doc is shared with. Not HMR-instant, but URL-stable across sessions,
policy-independent, and it doubles as the review surface for the onboarded
cohort — the same loop they'll use to show you their widgets.

**Optional tier — true HMR via tunnel (spike, ~30 min in a configured
environment):** ngrok is the only mainstream tunnel whose agent supports both
an outbound HTTP proxy (`proxy_url` → `$HTTPS_PROXY`) and custom root CAs
(`root_cas` → `/root/.ccr/ca-bundle.crt`, required because the egress proxy
re-terminates TLS). cloudflared does not honor proxies for its tunnel
transport (and QUIC/UDP is blocked); localtunnel's raw-TCP protocol is a poor
fit. Requirements: environment network policy allowing ngrok's edge/API
domains (or full access), `NGROK_AUTHTOKEN` env var, a static ngrok domain so
the Grist URL survives sessions, and Vite `server.allowedHosts` +
`server.hmr: { protocol: "wss", clientPort: 443 }`. Caveats: three
independent failure points (policy, proxy traversal, TLS interception),
ngrok free-tier browser interstitial inside the Grist iframe, tunnel dies
with the container. Document as a power setup only if the spike succeeds;
the primary loop above is the supported path.

## 5. Deferred — after the plan above (decided 2026-07-12)

Two items, explicitly not now — captured here so they aren't lost, and
because the second one changes how the first should ultimately work.

### 5.1 — Validate staging (`next`) publishes against a real widget, not just workspace-linking

`core-ci.yml`'s `build-widgets` matrix (added alongside the staging/rc-publish
mechanism) builds every `widgets/*` package against `packages/core` via
`workspace:^` — the exact in-PR source, with no publish step. That's the
tightest possible check, but it never touches npm packaging at all (the
`exports` map, the `files` list, subpath resolution). `smoke-external-install`
does exercise real npm packaging, but only for the minimal template, never a
real widget.

Gap: nothing currently installs a `publish-staging`-job-published `X.Y.Z-rc.N`
into a real widget via a genuine `npm install` and builds it. Proposed:
extend that job so that, right after publishing, it also copies
a real widget out of the workspace (same technique
`scripts/smoke/external-install.sh` already uses for the template), points
its dependency at that exact just-published version, and builds — so every
staging publish proves itself against real widget code through the actual
install path, automatically.

**This item is superseded in shape, not in need, by 5.2 below** — see there.

### 5.2 — Extract each `widgets/*` product widget into its own dedicated repo

`gantt`, `world-map`, `news-feed`, `ask-genial`, `create-email-draft`,
`upload-with-ai` (and `v0-minimal-demo` — categorize when this comes up: is
it a product or a demo?) move out of this monorepo into their own repos,
each depending on `grist-widget-sdk` from npm (`^0.x`, real semver range) like
any external consumer — no more `workspace:^`.

**What stays:** `apps/playground`'s demo widgets (hello-world, form-edit,
task-board, bulk-mark-done, schema-preview, schema-migration,
attachment-gallery, widget-options, safe-parse, …). These exist purely to
back the docs/guide/cookbook and the `// @example` type-check contract — they
must always test against the exact in-progress SDK source with no publish
step, which is precisely what workspace-linking gives them. Extraction is
about *product* widgets, not documentation fixtures.

**Why this is worth doing, and why it's natural *after* Phase 2, not before:**
each dedicated widget repo becomes, mechanically, exactly what
`create-grist-widget` scaffolds for an external developer — npm dependency,
its own two-channel deploy workflow (`v<version>/` + `latest/` + `dev`
preview), its own repo. So extraction isn't a bespoke migration; it's
"run the same onboarding kit against our own widgets" — which also makes our
own product widgets the standing, continuously-exercised proof that the
external path actually works, not just the toy template.

**What this changes, to work out when it comes up (not now):**

- `core-ci.yml`'s `build-widgets` matrix loses its subject — there's nothing
  under `widgets/*` to workspace-link against anymore. The "test against real
  widgets" loop then has to become the external kind by necessity: 5.1's
  "install the just-published staging version into a real widget" idea stops
  being an enhancement and becomes the *only* mechanism left, likely
  triggered from each widget's own repo (e.g. reacting to a new `next`
  publish) rather than from this monorepo.
- `deploy-widgets.yml` / `publish.mjs` (versioned releases, dev channel,
  manifest, self-reload) currently assume widgets live under `widgets/*`
  here. Each extracted repo needs its own copy of this pipeline (ideally a
  shared reusable workflow rather than N forked copies) — same shape as D4's
  "template ships its own deploy workflow."
  - **`manifest.json` still generated from here** (D2) — an extracted widget
    repo has no way to update this repo's `gh-pages` manifest itself, so the
    manifest-generation step needs a path to entries that live in other
    repos: either each widget repo's release workflow triggers a
    `repository_dispatch`/reusable-workflow call back into this repo to
    refresh `manifest.json`, or the manifest generator is changed to read a
    small declarative list (repo + widget metadata) instead of scanning
    `widgets/*/package.json` directly.
- **Deliberate loss of atomicity, not an oversight:** today one commit here
  can bump the SDK and have every workspace-linked widget pick it up in the
  same build. Post-extraction, each widget repo upgrades its own `^0.x`
  dependency on its own schedule — the same isolation already designed for
  third-party consumers, now applied to the maintainer's own widgets too.
- Visibility/repo-per-widget decisions (public showcase vs. private,
  issues/PRs surface) — same category of question as the private-monorepo
  ripple in D4/D6, not decided here.

### 5.3 — Wire `apps/playground`'s widget build into CI

Checked directly (grepped every workflow file): **nothing currently runs
`pnpm --filter playground build:widgets` — or root `pnpm test` at all — in
any GitHub Actions workflow.** Today, no CI protects the docs' `// @example`
type-check contract or the cookbook/demo widgets from an SDK regression;
that's a real, standing gap, independent of `build-widgets` (5.2's subject).

**Complementary to `build-widgets`, not a substitute for it — different
failure classes:** playground's demos (`hello-world`, `form-edit`,
`task-board`, `safe-parse`, …) are source subfolders inside *one* package,
built together by one shared `tsc -b && vite build --config
vite.widget.config.ts` — one tsconfig, one vite config, a minimal shared
dependency set (React + the SDK, essentially). They deliberately teach one
guide concept at a time and never touch what real widgets do: `gantt` pulls
in `@dnd-kit/*` + `jotai`; `world-map` pulls in `maplibre-gl`;
`upload-with-ai` pulls in `pdfjs-dist`; `ask-genial` pulls in `@ai-sdk/openai`
+ `@rive-app` + `@xyflow/react`. A regression specific to how the SDK
interacts with any of that — or with a real widget's own independent
`vite.config.ts`/`tsconfig.json` — would never surface in the simpler,
shared-config demos. Keep both: `build-widgets` (5.2) for real production
complexity, this for the docs/teaching contract.

**Proposed:** a step (or job) in `core-ci.yml` running
`pnpm --filter playground build:widgets` on any PR touching `packages/core` —
cheap (one build invocation, not a matrix), and it's the check that would
actually catch a broken docs site before merge.
