# Releasing `grist-widget-sdk` and `create-grist-widget`

> Read this before touching `.github/workflows/release.yml`, the `changeset`
> job of `.github/workflows/ci.yml`, `.github/workflows/template-canary.yml`
> or `.changeset/`. The weekly train itself is the `release-train` skill
> (`.claude/skills/release-train/`).

Releases are driven by **[Changesets](https://github.com/changesets/changesets)**
and published to npm via **Trusted Publishing (OIDC)** from GitHub Actions — no
long-lived `NPM_TOKEN`. (npm is deprecating 2FA-bypass CI tokens: account
actions ~Aug 2026, direct publishing ~Jan 2027.)

`packages/core` (`grist-widget-sdk`) and `packages/create-grist-widget`
(`create-grist-widget`) are published; every other workspace package is
`private`. Their versions are fixed together via changesets
(`.changeset/config.json` `fixed`), so a release touching either bumps and
republishes both to the same version number: `create-grist-widget` x.y.z
always scaffolds with `grist-widget-sdk` x.y.z.

## One-time setup — **required for every new publishable package**, not just the SDK

**npm Trusted Publishing (OIDC) can only be configured on a package that
already exists on the registry** — there's no npm package settings page to
attach a Trusted Publisher to until the name has been claimed at least once.
Skipping this for a brand-new package fails with a confusing
`npm error code E404` from inside `changeset publish` the first time CI tries
to publish it (hit for real with `create-grist-widget`'s first release,
2026-07-12 — see CHANGELOG). Any future new publishable package needs the
same two steps:

1. **Claim the name** with a first manual publish (already done for
   `grist-widget-sdk@0.2.0` and `create-grist-widget@0.1.0` — see
   *Manual publish* below).
2. **Add a Trusted Publisher** on <https://www.npmjs.com/> → the package's
   own **Settings → Trusted Publishing** → GitHub Actions:
   - Repository: `ArthurBlanchon/grist-widget-sdk`
   - Workflow: `.github/workflows/release.yml`

   (Same repo + workflow file for every package — Trusted Publisher config is
   per-*package*, not per-workflow-file, so this doesn't run into the
   one-trusted-workflow-file-per-package limit noted below.)

   After this, CI publishes with no stored token. npm only allows **one**
   trusted workflow file per package, which is why everything that publishes
   lives in this single file. It runs on pushes to `main` only.
3. **Bind publishing to `main`** (once per repository, then once per
   package's Trusted Publisher):
   - GitHub → Settings → Environments → `npm` (created by `release.yml`'s
     first run; create it by hand otherwise) → **Deployment branches and
     tags: Selected branches → `main`**.
   - On each package's npm **Trusted Publishing** settings, set
     **Environment** to `npm`.

   The trigger already limits `release.yml` to `main`, but a branch with a
   modified copy of the file could request an OIDC token of its own. With
   the environment restricted to `main` and named on npm, such a token is
   refused. Agents push branches to this repo, so this is what keeps them,
   and anyone else with write access, from publishing
   (`docs/history/2026-11-01-widget-lifecycle-plan.md`, U2).

## Day-to-day: add a changeset per change

Any PR that changes the published package includes a changeset:

```bash
pnpm changeset
# pick grist-widget-sdk, choose patch / minor / major, write a one-line summary
```

This writes a `.changeset/*.md` file — commit it with your PR. During `0.x`,
breaking changes are a **minor** (`0.3.0`); everything else is a **patch**.
(Repo/CI-only changes that don't affect the published package need no changeset.)

**Enforced by CI**: the `changeset` job of `.github/workflows/ci.yml` fails any PR
that touches `packages/core/src/`, `packages/create-grist-widget/{src,scripts}/`,
or `templates/grist-widget-template-vite/` (the template embedded into
`create-grist-widget` at publish time) without adding a `.changeset/*.md`
file — catches the "merged without a changeset, so nothing actually
published" mistake before it lands instead of after a release quietly ships
nothing (or, for the template specifically, ships stale content).

Dependabot pull requests are the one exception: Dependabot can't run
`pnpm changeset`, so the check lets a pull request authored by
`dependabot[bot]` through. Nothing commits onto Dependabot's branches: a
foreign commit stops Dependabot from rebasing them, and a push with
`GITHUB_TOKEN` leaves their CI waiting for approval. The release train adds
the changeset instead (below).

Two changelogs, two audiences:

- **`packages/core/CHANGELOG.md`** — the npm package's own changelog, fully
  **generated by Changesets** from your one-line summary above. Ships in the
  tarball; this is what `npm view` / the npm page shows. You don't hand-edit it.
- **[`/CHANGELOG.md`](../../CHANGELOG.md)** (repo root) — the broader,
  hand-curated project history (widgets, docs, tooling, process), still
  maintained manually and rendered on the docs site.

## Cutting a release (automated)

`.github/workflows/release.yml` runs on every push to `main`:

1. **With pending changesets** → it opens/updates a **"Version Packages" PR**
   that bumps `packages/core/package.json` and writes the new version's
   entries into `packages/core/CHANGELOG.md`, consuming the changeset files.
2. **Merge the Version PR** → the workflow runs again and, with no pending
   changesets, **publishes to npm over OIDC** and creates the git tag +
   GitHub Release.

So a normal release is just: merge feature PRs (each with a changeset) → merge
the Version PR. No local publish, no tokens, no OTP.

### The release train: once a week

The Version Packages PR collects every merged changeset until it is merged,
so releases are batched by merging it **once a week**, or at once for a
security fix. Widgets install a version only once it is a day old (pnpm's
`minimumReleaseAge`): releases hours apart would have them upgrade to a
version already replaced. Before merging it:

1. Add the routine changeset for the Dependabot updates the release
   carries, if any reached a published package (the template, or the SDK's
   own `dependencies`):

   ```bash
   node scripts/release/routine-changeset.mjs           # dry run: what it would write
   node scripts/release/routine-changeset.mjs --write   # .changeset/routine-dependencies.md
   ```

   Commit it in a pull request; once merged, the Version Packages PR
   includes it.
2. Read the Version Packages PR's changelog entries: they are what widget
   owners read when upgrading.
3. Merge it. A day later, the reference widgets take the release
   (`TODO.md`).

### `CHANGESET_PUSH_TOKEN` (optional — makes bot pushes run CI)

`release.yml` pushes commits on its own (the Version Packages branch, then
the release tags). Pushed with the default `GITHUB_TOKEN`, GitHub parks
every CI run they trigger as **action_required** — the PR shows only
the Cloudflare check until someone re-runs the runs by hand from the
Actions tab, and unapproved runs expire as failures after 30 days.
`GITHUB_TOKEN` also can't push a tag whose history introduces
`.github/workflows/` changes (hit on `create-grist-widget@0.3.2`).

It uses the `CHANGESET_PUSH_TOKEN` secret when it exists and falls back to
`GITHUB_TOKEN` otherwise, so nothing breaks without it (this repository runs
without it: approve the Version Packages PR's runs by hand). To set it up:

1. GitHub → Settings → Developer settings → **Fine-grained personal access
   tokens** → Generate new token. Repository access: **only**
   `ArthurBlanchon/grist-widget-sdk`. Permissions: **Contents**, **Pull
   requests** and **Workflows**, all *Read and write* — nothing else.
2. In this repo, Settings → Secrets and variables → Actions, add it as
   `CHANGESET_PUSH_TOKEN`.
3. Note the expiry date. **An expired token fails every push** (the release
   publishes to npm, then its tag push is rejected) — rotate it before then,
   or delete the secret to fall back to `GITHUB_TOKEN`.

Verify: `npm view grist-widget-sdk version` and the repo's Releases page.

> **Provenance**: npm attaches a provenance attestation to every version
> published through Trusted Publishing from this public repo (no setting
> needed): `npm view grist-widget-sdk@<version> dist.attestations` shows it,
> and npmjs.com links each version to the commit and workflow run that
> built it.

## Post-release verification (template canary)

`.github/workflows/template-canary.yml` runs after a `release.yml` run on
`main` that published: its first job checks that the commit is the one
tagged `create-grist-widget@<version>`, and skips the canary otherwise (a
push that only updated the Version Packages PR). It first waits (up to 10 minutes) until npm actually *serves*
the versions on the triggering commit — `workflow_run` fires once
`npm publish` returns, not once the registry serves it, and on 0.3.17 that
gap (~100s) made it scaffold the previous release and break the promoted
deploy. Then it does two things on
[`arthurblanchon/grist-widget-template`](https://github.com/arthurblanchon/grist-widget-template):

- **`dev`** scaffolds from the *actual published* `create-grist-widget@next`,
  falling back to `@latest`. No `next` exists, and nothing publishes one
  since pre-releases were retired, so in practice it matches `@latest`. It's
  pushed on top of `dev`'s own real history, then asserts the
  resulting GitHub Pages URL comes up with real content. Automates the same
  check the `run-grist-widget-template-deploy` skill does by hand.
- **`main`** is unconditionally force-pushed every run from a fresh
  `@latest`-only scaffold — promotion is automatic, not a manual PR. `main`
  is a distribution artifact for this reference repo, same as any real
  scaffolded widget's own `main` once its first-release guard has run (see
  `resetBranchesIfFirstRelease` in `packages/create-grist-widget/src/deploy.mjs`).

> ⚠️ **`main` is only ever force-pushed from `@latest`, never from `dev`.**
> `dev` follows `create-grist-widget@next` whenever one exists (none does,
> and nothing publishes one since pre-releases were retired), so this
> workflow keeps the two scaffolds — and the two push targets — completely
> separate: an unreleased build could never reach `main`. There used to be an
> intermediate `canary/latest` branch a human promoted into `main` by hand;
> that manual step was retired as non-negotiable once the template became
> the front door (a forgotten promotion would silently start every "Use
> this template" user on a stale pinned SDK, with nothing to catch it).

Needs `TEMPLATE_CANARY_DEPLOY_KEY`: an SSH deploy key with write access,
scoped to *only* that one reference repo (not a PAT — a leaked deploy key
can't reach anything else). To rotate it: generate a new keypair
(`ssh-keygen -t ed25519 -f canary_key -N ""`), replace the deploy key on
`grist-widget-template` (Settings → Deploy keys), update the
`TEMPLATE_CANARY_DEPLOY_KEY` secret here, then delete the local keypair
files.

## Testing a change before it's released

Nothing publishes to npm except a merge to `main`. There is no pre-release
channel: `publish-staging`, which published an `-rc.N` SDK tagged `next` from
any branch, was retired on 2026-11-01. It was the only path that could
publish from a branch other than `main`
(`docs/history/2026-11-01-widget-lifecycle-plan.md`, U2 / D1).

To try an unreleased SDK in a real widget, install a packed build:

```bash
pnpm --filter grist-widget-sdk build
(cd packages/core && pnpm pack --pack-destination /tmp)
# then, in the widget (on a throwaway branch):
pnpm add /tmp/grist-widget-sdk-<version>.tgz
```

A local tarball isn't subject to pnpm's 24 h `minimumReleaseAge`, and nothing
reaches npm. Don't commit that dependency; go back to the registry version
once the release is out. The Real widgets workflow does the same for the
reference widgets on every SDK pull request
([Real widgets](./real-widgets.md)).

The old `next` dist-tag (`0.2.2-rc.0`, from the staging channel) was removed
on 2026-11-08; `latest` is the only tag.

## Manual publish (fallback / first publish)

For the one-time name claim on any new publishable package (see above — this
is a hard requirement, not optional, before OIDC can work at all for that
package), or if OIDC is unavailable. Requires an npm account with publish
rights + 2FA.

```bash
pnpm install --frozen-lockfile
pnpm --filter <package> run build    # packages/create-grist-widget: embeds template/
cd packages/<package>                # core, or create-grist-widget
pnpm pack --dry-run          # sanity-check the tarball contents
pnpm publish --access public # add --otp=<code> when 2FA prompts
```

`packages/core/CHANGELOG.md` is real and git-tracked (Changesets-maintained, see
above). `LICENSE` is copied in from the repo root by the `prepack` hook
(git-ignored inside `packages/core`); `prepublishOnly` rebuilds `dist/`.

## Pitfalls found live

- **Merging without bumping the version publishes nothing.** A widget's
  release build skips a version whose directory already exists, and CI
  reports success either way: check the diff, not the run's colour.
- **A `gh-pages` branch seeded from another repository can squat on a
  version path** (GitHub's "Use this template" → "Include all branches"
  copies the template's own `gh-pages`). `grist-widget-deploy`
  (`packages/create-grist-widget/src/deploy.mjs`) counts a version as
  published only when its `showcase-meta.json` names the current
  repository, and a repository's first real release clears foreign content.
- **`updateInternalDependencies: "patch"` bumps every workspace package
  that depends on a bumped one, private or not.** The template's `version`
  must stay `0.0.1` (a fresh scaffold's version belongs to its author), so
  the template and `examples` are in `.changeset/config.json`'s `ignore`,
  and `build-template.mjs` sets the embedded template's version to `0.0.1`
  whatever its source says.

## The template's reference repository

On both of `grist-widget-template`'s branches, `scripts/template-repo-extras.mjs`
adds what the widget registry requires and a scaffold doesn't have: this
repository's MIT `LICENSE` (with `"license": "MIT"` in `package.json`) and
the README's install URL. A real widget picks its own licence and its first
release writes its install URL; the reference repository is replaced by a
fresh scaffold on every release, so the canary writes both.
