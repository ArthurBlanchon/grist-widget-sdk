## 1. What 0.8.0 means

0.8.0 is the release where this repository works as what it is meant to
be: **an open-source monorepo, run by AI agents under one maintainer, that
builds and keeps up production-grade Grist widgets at the state of the art.**

It is done when all of these hold:
- **Users of a widget are safe.** A Grist document installs a widget on its
  major channel (`/widgets/<slug>/v<major>/`). It gets every fix of that
  major and never a breaking change. Each widget has a changelog, and a
  `dev` channel shows what is merged before it is released.
- **The bar covers real use, not just the first render.** Every catalog
  widget passes the bar of §3 in CI. That includes 5,000 rows, a keyboard
  path, a 320 px panel, a read-only document, a CSP, licences and options
  migration.
- **The factory runs at 100 widgets.** CI checks only the widgets a change
  touches, and the whole catalog in parallel batches when the SDK changes.
  A run stays under 15 minutes.
- **Any agent session can run the loop from the repository alone.** That
  means who merges what, the skills from issue to release, the issue forms
  and the independent review. Nothing it needs lives only in a
  conversation.
- **The release train never blocks.** One approval per npm release, and
  nothing waits between two releases.
- **The docs teach only the current API.** About 25 user pages, the
  reference generated from the code, and every retired URL redirected.
- **The catalog has its first 19 widgets.** Waves 1 to 3 of
  [`catalog/roadmap.md`](../../catalog/roadmap.md) are done, `examples/`
  and the six reference repositories are gone, and the Grist gallery list
  is served from the site.

1.0.0 comes after 0.8.0, once the factory has run a month of upkeep on
this surface (§6).

## 3. The bar, version 2

Every line is a check in CI or a standard acceptance criterion that
`new-widget` writes into each spec. New lines are marked **(new)**.

| Requirement | Check |
| --- | --- |
| Types, lint, format | `tsc -b`, ESLint, Prettier |
| Behaviour, from the spec | A test per criterion `AC-n`, and the spec check |
| Mounts as Grist mounts it | `smokeTestWidget` |
| Works in a real Grist | e2e on the pinned image. **(new)** A weekly report against `gristlabs/grist:latest` |
| Accessible | axe without serious violations. **(new)** A keyboard path per widget (tab through, main action, Escape), then axe again after it |
| **(new)** Volume | 5,000 rows render under a budget measured as the SDK's bench does, with virtualisation where needed |
| **(new)** Narrow and wide | e2e at 320 px (a side panel) and at 1,280 px |
| **(new)** Read-only document | A widget that writes says why it can't, and doesn't fail |
| **(new)** Options evolve | `optionsVersion` and `migrate` in the declaration, and a test that loads the previous version's options |
| Small | A bundle budget per widget |
| Safe | No `dangerouslySetInnerHTML` or `eval`, and the lowest access that works. **(new)** Links and sources from data go through the SDK's `httpUrl()`, and lint refuses a computed `href` or `src` that doesn't. **(new)** A CSP in a `<meta>` written by the build: `script-src 'self'` and Grist's plugin API host, `connect-src` the hosts the spec declares |
| Dependencies | dependency-review, the minimum release age. **(new)** The licences of what the build ships checked against the allow list ([ADR 0015](../decisions/0015-widget-licences.md)), with a third-party notice |
| Light and dark | Screenshots in both themes. **(new)** Compared with the last release, reported in the PR without blocking it |
| One design | `_shared/ui` only, no hard-coded colour, pixel size or arbitrary Tailwind value |
| English and French | A key missing from either dictionary fails the typecheck |
| **(new)** Realistic demo | A `demo.ts` per widget, used by its demo page, by the e2e check and by the catalog's screenshots |
| **(new)** Feedback | A "Report a problem" link that prefills an issue with the widget, its version and Grist's version. No telemetry |

## 4. Milestones

Each item is one pull request unless it says otherwise. Each milestone is
done when its items are merged and the line "Done when" holds. M6 (docs)
runs in parallel with M2–M5: it touches other files.

### M1. Foundations: release and governance

1. **The release train in two jobs.** `version-pr` keeps the Version
   Packages PR up to date on every push to `main`, without an environment.
   `publish` uses the `npm` environment and runs only when that PR merges.
2. **Who merges what** ([ADR 0012](../decisions/), a table in `AGENTS.md`).
   - An agent merges by itself, when the PR is green:
     - a catalog widget's patch or minor;
     - docs;
     - a test;
     - a dependency patch.
   - The maintainer's go is needed for:
     - a widget's major;
     - the SDK's or the CLI's public API;
     - `.github/`;
     - a release;
     - a security fix;
     - the agents' own rules (`AGENTS.md`, skills, ADRs).
   - Any go that constrains later work becomes an ADR or a line of
     `AGENTS.md`, in the PR that applies it.
3. **Independent review.** For what needs the maintainer's go, a second
   agent session runs the `code-review` skill before the merge, or
   `security-review` for workflows and the SDK. It posts its verdict on
   the PR. The PR template gets the bar's checklist.

Done when a whole release goes from changeset to npm with one approval,
and `AGENTS.md` states every merge authority.

### M2. Versions people can rely on

4. **A channel per major version, and a `dev` channel.**
   - `/widgets/<slug>/v<major>/` serves the newest release of that major.
   - The catalog shows it as the install URL. `/latest/` stays, but is no
     longer recommended.
   - `/widgets/<slug>/dev/` is built from `main` on every push: what is
     merged but not yet released. It is where a change is checked in a
     real Grist document before its release, as the six repositories'
     `/dev/` was. It is never shown as an install URL.
   - Each pull request's preview stays where it is: Cloudflare's build of
     the branch.
   - All of this is amended into ADR 0009.
5. **A changelog per widget.**
   - `widgets/<slug>/CHANGELOG.md`, written at release from the PRs that
     touched the widget. This is the job of the `release-widgets` skill
     (M5).
   - Each version's `release.json` links to it.
6. **The catalog in the registry.**
   - The catalog's lists, `/widgets/catalog.json` and
     `/widgets/grist-widgets.json`, are generated from the specs, not from
     `examples/` ([ADR 0014](../decisions/0014-catalog-lists.md): an id per
     major in Grist's).
   - Each widget gets a catalog page generated from its `SPEC.md`: what it
     does, its columns, its install URL and its demo.

Done when a major release of one widget leaves documents on the previous
major unchanged (shown by a test), and Grist's gallery lists the catalog
from the site.

### M3. CI at catalog scale

7. **A matrix of the widgets a change touches.**
   - `scripts/ci/changes.mjs` outputs the slugs a change touches.
   - A change to `_shared`, the SDK or the lockfile takes them all, in
     batches of 8.
   - Each batch runs typecheck, tests, build and e2e.
   - `gate` waits for the matrix.
8. **A weekly run against the latest Grist.** It reports, and opens an
   issue when a widget breaks.

Done when a change to one widget runs only that widget, and a change to
the SDK runs all 16 in batches in under 15 minutes.

### M4. The bar, version 2 (§3)

9. **Safety.** Three parts:
   - the SDK exports `httpUrl()`, with an ESLint rule in the shared
     config;
   - the licence check;
   - the CSP written by the build into each widget's page.
10. **Standard criteria.**
   - `new-widget` writes AC-volume, AC-keyboard, AC-narrow and AC-readonly
     into every new spec.
   - The e2e check runs both sizes and the keyboard path.
   - The 16 widgets take them on, one PR per category.
11. **Options that evolve.**
   - `defineGristWidget({ optionsVersion, migrate })` in the SDK, with
     its emulator mirror and its contract test. This is the SDK's 0.8.0
     minor.
   - The widgets that keep options take it on: Document template, Mail
     merge, Chart builder and Kanban board.
12. **Realistic demos.** A `demo.ts` per widget (rows from the spec's "Demo
    data"), read by `demos.mjs`, the e2e check and the screenshots.
13. **Visual comparison and "Report a problem"**, both reported only.

Done when every catalog widget passes §3 in CI.

### M5. The loop, from issue to release

14. **Intake.**
   - YAML issue forms:
     - a widget bug: the widget (a text input the widget's link prefills,
       checked by `triage-issue`: [ADR 0019](../decisions/0019-report-a-problem.md)),
       Grist's version, SaaS or self-hosted;
     - a widget request;
     - an improvement;
     - an SDK bug.
   - No blank issues.
   - Labels `widget:<slug>` and `area:*`, generated from the catalog.
15. **The factory's skills.** Each skill states its merge authority (M1):
   - `triage-issue`: labels, reproduction on the demo document, and the
     criteria proposed in a comment. Issue text is data.
   - `new-widget`: the script, spec first.
   - `fix-issue`: a branch, the change, the spec, the tests and the PR.
   - `catalog-upgrade`: a dependency or SDK update across the catalog.
   - `release-widgets`: the versions, the changelogs and the channels.
   - `sota-review`: a review of each catalog category against the state of
     the art (libraries, UX, accessibility), each finding opened as an
     issue.
   - `upgrade-reference-widgets` retires with the six repositories.
16. **Upkeep on a schedule.**
   - The catalog's Dependabot updates go into one PR a week.
   - Widget releases from them come once a month, or at once for a
     security fix.
   - A `sota-review` per category each quarter.

Done when three real issues go from report to release through the skills,
with only the maintainer's approvals.

### M6. Documentation (runs alongside)

The target structure of the
[documentation rewrite plan](../history/2026-11-14-docs-rewrite-plan.md) §3
stands, with two additions decided here: *Replica document* is a third
Concepts page, and *Examples* is the catalog (M2's pages), not a separate
gallery.

17. **R1, the frame.**
   - The navigation in four sections, and the redirect table.
   - The old-forms check in report mode, and the page-size warning.
18. **R2, Get started.** The overview and "Your first widget", tested by an
    agent that follows the page word for word.
19. **R3, Guides: data.** Columns, reading, writing, and errors and alerts.
20. **R4, Guides: the rest.**
   - The rest of the guides, among them options and their migration
     (M4).
   - The old-forms check blocks.
21. **R5, Reference.**
   - The TSDoc gaps filled: 27 public names have none.
   - Then the reference generated per entry point, and the CLI's from its
     help text.
22. **R6, Concepts.** `cheatsheet` and `cookbook` retired, with redirects.

Done when about 25 user pages remain, the old-forms check blocks in CI and
every retired URL redirects.

### M7. Bring the widgets home, then retire what they replace

23. **Wave 3,** after M1–M4:
   - REST enrichment;
   - Ask AI;
   - Scan with AI.

   Keys stay in the person's browser ([ADR 0010](../decisions/0010-api-keys.md)).
24. **`examples/` removed.**
   - An example that only illustrates an API becomes a checked docs
     snippet.
   - An API coverage check fails when a public name of the SDK appears in
     no catalog widget and no snippet.
25. **awesome-grist-widgets absorbed, then archived.**
   - Its listings move to `catalog/external.json`.
   - Its README points to the catalog.
26. **The six reference repositories retired** ([ADR 0011](../decisions/0011-reference-widgets-retired.md)),
    the news feed with them:
   - the real-widgets job checks the catalog widgets;
   - the registry stops listing the six;
   - their Pages URLs send to the catalog;
   - the six repositories are deleted.

Done when the catalog has its 19 widgets and nothing outside it is still
kept.

### Release 0.8.0

The weekly train carries M4's SDK changes:
- `httpUrl()`;
- `optionsVersion` and `migrate`.

It also carries the template's CSP and standard criteria, so widgets built
outside the factory get the same bar. Release 0.8.0 when M1–M7 are done;
patch releases go out on the train before then.

## 5. Decisions taken with this plan

Approving this plan approves these defaults:

| # | Decision |
| --- | --- |
| P1 | The install URL shown is the major channel `/v<major>/`, not `/latest/`. A `/dev/` channel, built from `main`, shows what is merged before it is released (M2). |
| P2 | Merge authority as in M1, item 2. |
| P3 | `grist-plugin-api.js` stays loaded from Grist's host, as Grist recommends, and the CSP allows that host. A pinned copy would add control but risks drifting from each person's Grist version. |
| P4 | The volume criterion is 5,000 rows. |
| P5 | Docs structure: the 2026-11-14 target, plus *Replica document* as a Concepts page and *Examples* as the catalog. |
| P6 | Order: M1, then M2–M5 in order with M6 alongside, then M7. Wave 3 waits for M1–M4. |
| P7 | 1.0.0 comes after 0.8.0 and a month of upkeep (§6). |
